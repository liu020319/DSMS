# 统一小程序入口路线图

状态：规划，不属于 2026-08-22 DSMS OBS 发版范围。

## 产品结构

一个小程序主入口，按功能拆成独立分包：

```text
主包：登录、首页、模块入口、消息与个人中心
  |- DSMS 家庭用药协作分包
  |- 个人记账分包
  `- 软件工程服务与学习辅导分包
```

分包不是只为目录好看。它减少首次下载体积，也能让页面、权限和发布节奏相互隔离。

## 数据与存储边界

- DSMS：医疗、订单、付款、发票和收货证据；使用私有 `dsms-file`，严格家庭权限。
- 记账：账本、账户、分类、预算、周期账单、统计和导出；单独数据表和 OBS 前缀，不读取 DSMS 资金台账。
- 软件服务：案例、需求登记、沟通记录、报价、里程碑、交付物、部署工单和售后；不得访问家庭医疗数据。
- 个人博客：网站内容与作品展示；使用 `xiaoliudev`，与小程序业务文件分开。

## 技术路线

- 小程序端优先采用 uni-app 或原生小程序组件，复用 Spring Boot API 和业务规则；现有 Vue + Element Plus 页面不能直接当原生小程序发布。
- 后端先保持模块化单体：统一认证、通知、文件中心和审计作为基础模块，DSMS/记账/服务中心分别作为业务模块。
- 体量和团队未达到微服务必要条件前，不为简历强拆 Spring Cloud、MQ 或多数据库。
- 后期满足真实条件时再引入：Redis 会话/热点、对象直传签名、异步任务、接口限流、集中日志、指标监控和 CI/CD。

## 软件工程服务合规表达

可提供需求分析、技术辅导、代码讲解、功能开发、Bug 调试、测试、部署上线和运维。不承诺代写论文、替考或冒充学生完成学术成果。公开页面使用“软件开发 / 项目辅导 / 调试部署 / 技术咨询”等准确表述。

## 建议迭代顺序

1. 完成并上线 DSMS 私有文件中心和证据时间线；
2. 建立小程序 AppID、HTTPS 合法域名与基础主包；
3. 迁移 DSMS 的登录、订单、凭证和收货最小闭环；
4. 开发独立个人记账 MVP；
5. 开发软件服务需求与进度中心；
6. 做统一设计系统、消息聚合、埋点、监控和自动化发布；
7. 再做个人博客科技感重构，并与小程序互相导流。

## 企业级衡量方式

不按菜单数量打分。重点看模块边界、权限、审计、数据一致性、测试、可观测性、性能、可恢复发布、安全和真实业务闭环。每新增技术必须回答“解决了哪个已经出现的问题”。
